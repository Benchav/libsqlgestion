# Backup, restore and ERP migration

This guide is the operational contract for running LibSQLite as the primary
database platform for production ERPs. It covers what is backed up, how restore
works, how token rotation behaves and how to cut a system over from Turso Cloud.

## 1. Backup format by engine

| Database | Snapshot mechanism | Stored format | Restore |
| --- | --- | --- | --- |
| `LOCAL-FILE` SQLite | `VACUUM INTO` | `.db` | Copy into managed storage and open a local database |
| Dedicated `libSQL` runtime | `GET /dump?preserve_row_ids=true` | Verified `.db` (default) or `.sql` | Import the `.db`, or replay the `.sql`, then provision a **new** libSQL primary |
| Shared `sqld` namespace | `GET /dump` with `x-namespace` | Verified `.db` (default) or `.sql` | Same as dedicated runtime |
| Turso Cloud / external | Not managed here | — | Back it up with Turso before migration |

The libSQL dump is generated by the engine inside a read transaction. It is the
supported consistency mechanism for a live primary; do not back up a running
libSQL data file by copying pages manually.

`SNAPSHOT_LIBSQL_ARTIFACT` controls the stored artifact:

- `auto` (default): verified `.db` when replay verification is enabled, otherwise
  the legacy `.sql` dump.
- `sqlite`: verified `.db` only, matching Turso's `db export` experience.
- `both`: keep the legacy `.sql` and the verified `.db` (recommended during a
  transitional rollout; older backend versions can still restore the `.sql`).
- `dump`: raw `.sql` only (immediate behavior rollback without downgrading code).

Existing `.sql` snapshots remain downloadable and restorable in every mode.
Artifact names, checksums and sizes are stored in the existing snapshot
`metadata` JSON column, so switching modes requires no database migration.

### 1.1 Offsite copies (S3 / Cloudflare R2)

Local snapshots live on the same VPS and are **not** disaster recovery. The
panel can copy finished snapshots to an S3-compatible bucket:

**Settings → Offsite Backups (S3 / Cloudflare R2)**

Cloudflare R2 setup:

1. Create a **private** bucket, for example `libsqlite-backups`.
2. Create an R2 API token scoped to that bucket with Object Read & Write.
3. Copy the Access Key ID, Secret Access Key and the S3 endpoint
   `https://<account-id>.r2.cloudflarestorage.com`.
4. In the panel set endpoint, bucket, region `auto`, a prefix such as `prod`,
   the credentials, and **Save offsite settings**.
5. Press **Test connection**.
6. Upload one manual snapshot and validate the object and restore before
   enabling automatic uploads.

The access key is encrypted with `MASTER_KEY` before it is stored. It is never
returned by the API, written to audit logs or exposed to the frontend. Keep
`master.key`/`MASTER_KEY` in the same backup set as `control.db`; losing it makes
the stored S3 secret unreadable and requires re-entering it in the panel.

Upload policies:

- `daily` (default for R2 free): daily milestone snapshots plus manual/pinned
  snapshots. Keeps the free tier comfortable.
- `all`: every ready snapshot. Roughly 4–5 GB for the current hourly tiering;
  monitor growth.
- `manual`: only snapshots explicitly queued from the panel.

`SNAPSHOT_OFFSITE_REQUIRED=true` keeps local snapshots out of normal pruning
until their offsite upload succeeds. Use it only when disk capacity is monitored;
a persistent bucket failure can make the local snapshot set grow beyond its
retention policy. The default is `false`, where failed uploads are visible but do
not block local retention.

New remote objects use a human-readable layout with the database name directly
under the prefix:

```text
<prefix>/<database-slug>/<database-slug>_<YYYY-MM-DD_HH-mm-ss>_<shortSnapshotId>.db
<prefix>/<database-slug>/<database-slug>_<YYYY-MM-DD_HH-mm-ss>_<shortSnapshotId>.manifest.json
```

Example:

```text
libsqlite/insumosv1/insumosv1_2026-11-19_14-48-55_a1673e12.db
libsqlite/insumosv1/insumosv1_2026-11-19_14-48-55_a1673e12.manifest.json
```

Database names are slugified (lowercase, no accents, spaces replaced with
hyphens). If two databases in the workspace share a name, the short database ID
is appended to avoid collisions. Renaming a database only affects future
uploads; old objects remain under the previous folder and are still readable
through their manifest/object metadata. The manifest still records the project
and database IDs/names, so removing the project folder does not lose context.

Snapshots uploaded before this layout change keep their previous keys
(`<project>/<database>/...` or the original UUID layout). All layouts are
supported by remote retention and restore.

The manifest is uploaded last and records checksums, sizes, format, pinned
state and artifact list. Downloads and restores must verify that checksum before
using the file. Remote retention removes unpinned groups older than
`SNAPSHOT_OFFSITE_RETENTION_DAYS`; deleting or pruning a local snapshot does
**not** delete the remote copy. Pinned/manual snapshots are protected from
automatic remote retention.

Operational rules:

- The local snapshot remains the primary restore path.
- An R2 outage never blocks snapshot creation; upload failures are shown in the
  panel and retried with backoff.
- The uploader holds the same snapshot lease as downloads/restores, so local
  retention cannot unlink a file mid-upload.
- Keep the bucket private. The backend talks to R2; the browser never does.
- Configure an R2 lifecycle rule to abort incomplete multipart uploads after
  one day; a killed backend cannot always abort its own multipart parts.
- R2 free-tier limits (storage/operations) are not an SLA. Verify current
  limits and monitor bucket growth.

The optional `SNAPSHOT_OFFSITE_*` environment variables are bootstrap defaults
for headless installs. Values saved in the panel take precedence.

> **Image rollback caveat.** Rolling back to a backend release that predates
> SQLite exports is only safe while snapshots keep a `.sql` artifact. An older
> release treats a `.db` libSQL snapshot as a local SQLite file and copies it
> instead of provisioning a libSQL primary. Use `both` during the transition, or
> set `SNAPSHOT_LIBSQL_ARTIFACT=dump` and create a fresh `.sql` snapshot before
> downgrading. Never delete the last `.sql` copies until the new release is
> accepted in production.

Manual libSQL snapshots return a **pending** job immediately (`202`) and finish in
the background; the Restore points list polls until the snapshot is ready. This
avoids a proxy timeout while the engine exports a large database.

Every libSQL snapshot is:

1. Streamed to a temporary SQL dump.
2. Checked for a valid `BEGIN TRANSACTION` and a final `COMMIT` statement at the
   end of the file (a `COMMIT;` inside row data is not accepted).
3. Replayed into a temporary SQLite database (including triggers and FTS5
   virtual tables emitted through `writable_schema`).
4. Closed and reopened, then integrity-checked from disk. This matters because
   virtual-table definitions are written through `writable_schema`; checking on
   the same connection can accept a schema that does not survive reopening.
5. In `auto`/`sqlite`/`both`, the replay result is kept as the downloadable
   `.db` and stored with SHA-256 checksums. Source `user_version`,
   `application_id`, `page_size`, `encoding` and `auto_vacuum` are captured
   best-effort and reapplied. In `dump`, only the `.sql` is kept with
   `format=libsql-sql-dump`.
6. If materialization fails, a structurally valid `.sql` is kept as a ready
   snapshot with a visible warning instead of losing the backup.

Set `SNAPSHOT_LIBSQL_VERIFY_REPLAY=false` only if replay time is unacceptable
for very large databases. With `SNAPSHOT_LIBSQL_ARTIFACT=auto`, the snapshot then
stays in legacy `.sql` mode. With `sqlite` or `both` explicitly selected, replay
is mandatory because it produces the `.db`; a failure falls back to `.sql` with
a warning.

The dump reads a consistent snapshot but can run for a long time on a large ERP.
During that window WAL may grow because checkpointing cannot advance past the
reader. Schedule the first libSQL dump during low traffic, watch disk space and
avoid overlapping dumps. `SNAPSHOT_MAX_CONCURRENT=1` is intentional.

## 2. Recovery objectives

Define these per ERP before cutover:

- **RPO**: maximum acceptable data loss.
- **RTO**: maximum acceptable time to restore service.

The default scheduler creates a restore point every 60 minutes. That does **not**
provide a 5-minute RPO. If the business requires a lower RPO, increase the
frequency or add engine-level replication; a local snapshot alone cannot recover
committed writes that were never captured.

Snapshots stored on the same VPS are **not** an offsite backup. Copy or sync the
snapshot directory to independent storage and test that copy. Losing the VPS
also loses local snapshots.

For large libSQL databases, size the retention policy deliberately. The default
tiered policy keeps roughly the last 24 hours hourly, 72 hours every six hours
and 14 days daily. A 20 GB logical dump can consume hundreds of gigabytes under
that policy; reduce `SNAPSHOT_INTERVAL_MINUTES`, `SNAPSHOT_RETENTION_DAYS` or
disable scheduled libSQL dumps (`SNAPSHOT_LIBSQL_ENABLED=false`) and create
pinned manual snapshots at the cadence the business actually needs.

## 3. Restore procedure

1. Open the database detail page → **Restore points**.
2. Choose a snapshot and **Restore**.
3. The restore creates a **new database**; it never overwrites the live primary.
4. For a libSQL snapshot with a verified `.db`, the export is copied to a
   private temporary file, integrity-checked and imported into a fresh primary.
   For a legacy `.sql`, the dump is replayed first. The new database receives a
   new credential.
5. The download button offers the preferred artifact. In `both` mode the primary
   download is `.db`; the **SQL** action downloads the retained `.sql` dump.
6. Validate row counts, critical tables and application login on the new
   database.
7. Point the ERP to the new URL and token only after validation.

Snapshot checksums are verified before restore when `SNAPSHOT_VERIFY_ON_RESTORE`
is enabled. A `.db` restore is faster; a `.sql` restore is bound by replay time.
If the SQLite export is suspected to be corrupt, use the restore API with
`"artifactFormat": "sql"` to force the raw dump path. The restore request is
synchronous while the artifact is imported/replayed and the new primary is
provisioned. Allow enough proxy/request timeout for the largest database, or
perform the restore from a maintenance window. The live primary is never
overwritten.

If the local VPS was lost, recover from the offsite bucket:

1. Download the chosen object from R2 to the backend host (AWS CLI, rclone or
   the S3 API).
2. Download its `manifest.json` and compare the object SHA-256 with the manifest.
3. Run `PRAGMA integrity_check` on the `.db` copy.
4. Import/restore it through the same procedure used for a local snapshot.

Never stream an object directly from R2 into the restore path without a local
copy and checksum verification.

For a production incident:

```bash
# Inspect what will be restored before touching the ERP.
npm --prefix backend run test:external -- \
  "https://<restored-host>" "<new-jwt>" --embedded --deep
```

The `--deep` check creates a uniquely named temporary table, verifies
propagation to an embedded replica, deletes the marker and drops only that
table. Run it against a test or newly restored database, not the live primary
during business hours.

## 4. Token rotation and downtime

**Create new token** performs a guarded rotation:

1. A recovery journal is written to `auth.pem.rotation` **before** Docker is
   touched. It records the old container id/name, the previous verification key
   and, once known, the replacement container id and its new key.
2. The previous runtime is renamed, stopped and disconnected from the routing
   network.
3. A replacement starts with a new signing key and token.
4. The replacement must accept an authenticated query.
5. The new credential and metadata are persisted to the control database; the
   journal moves to the `committed` phase.
6. Only after that write succeeds is the previous runtime removed and the
   journal cleared.

If any step fails, the backend restores the previous `auth.pem`, inspects the
old container's real state, renames it back, reconnects it and starts it. Only a
replacement whose creation was positively confirmed is ever removed; a failure
in the initial rename can no longer delete the original runtime.

If the backend process is killed mid-rotation, startup reconciliation reads the
journal and compares it with the persisted runtime id:

- If the control plane points at the replacement, it starts that container with
  its **new** key and validates the persisted token. It never applies the old
  key to a committed replacement.
- If the control plane still points at the old runtime, it removes the
  unpersisted replacement, restores the old key and brings the previous primary
  back.
- Failed validation keeps the journal for manual inspection.

Rotation is not zero-downtime: it involves a short restart window and the old
token stops being valid after success. Schedule it during a maintenance window
and update the ERP immediately. Do not use **Create new token** as a routine
health refresh.

Before an ERP cutover, rehearse rotation on a disposable database: confirm the
new token works, the old token is rejected, and the runtime survives a backend
restart. The automated tests cover the Docker state machine and crash recovery,
but the first real rotation on your server remains the acceptance test.

## 5. Runtime health

The backend persists internal, backend and public route health. A monitor
refreshes stale results every 10 minutes and on startup, so health survives
backend restarts. Checks run with bounded concurrency and are only written when
the runtime identity (container id and signing key) is still the one that was
checked. A rotation that finishes during a health check can therefore never be
overwritten with stale metadata.

Configuration:

```env
RUNTIME_HEALTH_INTERVAL_MINUTES=10
RUNTIME_HEALTH_PUBLIC_TIMEOUT_MS=5000
RUNTIME_HEALTH_STARTUP_DELAY_SECONDS=20
RUNTIME_HEALTH_CONCURRENCY=4
```

A public health success means the backend resolved the host through DoH and
completed an authenticated query against the public URL. It does not prove that
an ERP's machine, corporate DNS or firewall can reach the same host. For that,
run the external test from the ERP network.

`/ready` reports control-plane readiness (control database reachable). It
returns `degraded: true` with the runtime summary when a tenant primary is
unhealthy, but it does not fail the backend, because an ERP primary issue must
not restart or unroute the admin panel. Use `/ready?strict=1` from an external
monitor if that monitor should alert on tenant runtime health.

## 6. Performance model

The Studio now:

- asks for schema metadata with `counts=0`;
- caches schema by `PRAGMA schema_version`, so repeated opens avoid re-reading
  every table;
- batches libSQL metadata reads per chunk instead of two round trips per table;
- loads rows immediately and runs `COUNT(*)` in parallel instead of waiting for
  the count before painting the grid;
- discards responses from a table/page that is no longer active;
- loads the exact row count only for the table being opened;
- keeps counts outside the schema cache. `schema_version` changes on DDL only,
  so caching a response with `COUNT(*)` would serve stale numbers after normal
  inserts and deletes. Requests with counts are always executed fresh.

For local SQLite, reads use a bounded WAL reader pool
(`SQLITE_READ_POOL_SIZE`, default 4) instead of sharing the single sqlite3
connection used for writes. This is what lets independent Studio/API reads run
concurrently. Remote libSQL clients already multiplex over HTTP and are not
affected by this setting.

The dashboard samples Docker stats with limited concurrency and serves a short
cache (`METRICS_CACHE_TTL_MS`, default 5000 ms).

Important limits:

- Increasing `DB_CONNECTION_POOL_MAX_SIZE` does not increase SQLite write
  throughput. Measure lock contention, transaction duration and disk latency.
- `SQLITE_READ_POOL_SIZE` improves concurrent local reads, not writes. SQLite
  still has a single writer.
- `SQLITE_PERFORMANCE_PROFILE` tunes the backend's local SQLite client. It does
  not change the `sqld` primary's configuration.
- `COUNT(*)` on a huge table is still a full scan; it now runs in parallel with
  the first page instead of blocking it. An index on the filtered/sorted columns
  is usually the larger win.
- Remote ERP reads from an embedded replica are local; writes to the primary
  still pay the network round trip.

## 7. Turso Cloud → LibSQLite cutover

### Before the window

1. Inventory every ERP database: size, tables, triggers, FTS/virtual tables,
   extensions, write rate and acceptable RPO/RTO.
2. Create a test database in LibSQLite and import a recent copy.
3. Run the deep external test from the ERP's network.
4. Record the exact ERP environment variables and the current Turso values.

### Migration window

1. Stop writes in the ERP (or put it in maintenance mode).
2. Export a final consistent copy from Turso.
3. Import it through the panel or **Server path**.
4. Validate schema objects, row counts and critical queries.
5. Change only the ERP environment:

   ```env
   TURSO_DATABASE_URL=file:/persistent/insbarrera.db
   TURSO_SYNC_URL=libsql://<host>
   TURSO_AUTH_TOKEN=<new-token>
   ```

6. Start the ERP and verify the embedded replica syncs.
7. Exercise login, a read and a write. Confirm the write appears in the primary.
8. Keep the old Turso database read-only until the observation period ends.

### Rollback

After the ERP has accepted writes in LibSQLite, reverting the URL is not enough:
those writes do not exist in Turso. Rollback requires exporting the LibSQLite
database and importing it back, or replaying the delta. Decide this before the
cutover and keep the first hours low-risk.

## 8. Command reference

```bash
# Local migration from legacy LOCAL-FILE to a managed primary.
npm --prefix backend run migrate:local-to-primary -- --mode=runtime --dry-run
npm --prefix backend run migrate:local-to-primary -- --mode=runtime --apply

# Remote + embedded replica + propagation test.
npm --prefix backend run test:external -- \
  "libsql://<host>" "<jwt>" --embedded --deep

# Comparable latency benchmark (run the same command against Turso).
npm --prefix backend run test:external -- \
  "libsql://<host>" "<jwt>" --bench --table=<table> --iterations=30

# Backend tests (114+ tests) and full quality gate.
npm --prefix backend test
npm test
```

Useful server checks:

```bash
docker logs --tail 200 <backend-container>
docker logs --tail 200 <runtime-container>
docker inspect <runtime-container> --format '{{json .State.Health}}'
```

## 10. First deployment of libSQL snapshots

Before enabling scheduled libSQL dumps on a production ERP:

1. Deploy with `SNAPSHOT_LIBSQL_ENABLED=false` if you want to choose the first
   window manually. For the safest transition use
   `SNAPSHOT_LIBSQL_ARTIFACT=both`.
2. Create one manual snapshot from the panel and confirm it reaches **Ready**
   with the **SQLite export · verified** badge. In `both` mode the `.sql` is
   also retained and downloadable.
3. Download the `.db`, open it with `sqlite3` and run `PRAGMA integrity_check`.
   Restore it into a test database and validate row counts.
4. Set the retention aggressively enough for the database size, including both
   artifacts while in `both` mode. `totalSizeBytes` in the API and UI reports
   the real footprint.
5. Switch to `SNAPSHOT_LIBSQL_ARTIFACT=sqlite`, enable scheduled dumps and
   monitor disk, WAL growth and the first run.
6. To roll back behavior without downgrading the image, set
   `SNAPSHOT_LIBSQL_ARTIFACT=dump` and restart. Snapshots already stored as
   `.db` remain downloadable and restorable by the current release.
7. Before any image downgrade, follow the image rollback caveat in section 1:
   keep or create `.sql` copies first. Once the new `.db` path has been accepted,
   avoid downgrading images without a tested import procedure for those files.

## 11. Known boundaries

- A single VPS remains a single point of failure. Snapshots restore data; they
  are not high availability.
- `latest` as the libSQL image tag can change the engine on redeploy. Pin the
  image digest or a specific release for production.
- HTTP `/dump` is a logical export. It can be slower than a physical copy for
  very large databases; measure the restore time with a real copy.
- The public route, certificate and DNS are separate from the data backup. A
  successful snapshot does not imply a working public hostname.
