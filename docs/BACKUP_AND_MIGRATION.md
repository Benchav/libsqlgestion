# Backup, restore and ERP migration

This guide is the operational contract for running LibSQLite as the primary
database platform for production ERPs. It covers what is backed up, how restore
works, how token rotation behaves and how to cut a system over from Turso Cloud.

## 1. Backup format by engine

| Database | Snapshot mechanism | Stored format | Restore |
| --- | --- | --- | --- |
| `LOCAL-FILE` SQLite | `VACUUM INTO` | `.db` | Copy into managed storage and open a local database |
| Dedicated `libSQL` runtime | `GET /dump?preserve_row_ids=true` | `.sql` | Replay into SQLite, verify, then provision a **new** libSQL primary |
| Shared `sqld` namespace | `GET /dump` with `x-namespace` | `.sql` | Same as dedicated runtime |
| Turso Cloud / external | Not managed here | — | Back it up with Turso before migration |

The libSQL dump is generated by the engine inside a read transaction. It is the
supported consistency mechanism for a live primary; do not back up a running
libSQL data file by copying pages manually.

Manual libSQL snapshots return a **pending** job immediately (`202`) and finish in
the background; the Restore points list polls until the snapshot is ready. This
avoids a proxy timeout while the engine exports a large database.

Every libSQL snapshot is:

1. Streamed to a temporary file.
2. Checked for a valid `BEGIN TRANSACTION` / final `COMMIT`.
3. Replayed into a temporary SQLite database (including triggers and FTS5
   virtual tables emitted through `writable_schema`).
4. Integrity-checked.
5. Stored with SHA-256 checksum and `format=libsql-sql-dump`.

Set `SNAPSHOT_LIBSQL_VERIFY_REPLAY=false` only if replay time is unacceptable
for very large databases. Structural validation still runs, but the backup is no
longer proven restorable at creation time.

The dump reads a consistent snapshot but can run for a long time on a large ERP.
During that window WAL may grow because checkpointing cannot advance past the
reader. Schedule the first libSQL dump during low traffic, watch disk space and
avoid overlapping dumps. `SNAPSHOT_MAX_CONCURRENT=1` is intentional.

## 2. Recovery objectives

Define these per ERP before cutover:

- **RPO**: maximum acceptable data loss.
- **RTO**: maximum acceptable time to restore service.

The default scheduler creates a restore point every 60 minutes. That does **not**
provide a 5-minute RPO. If the business requires a lower RPO, increase the
frequency or add engine-level replication; a local snapshot alone cannot recover
committed writes that were never captured.

Snapshots stored on the same VPS are **not** an offsite backup. Copy or sync the
snapshot directory to independent storage and test that copy. Losing the VPS
also loses local snapshots.

For large libSQL databases, size the retention policy deliberately. The default
tiered policy keeps roughly the last 24 hours hourly, 72 hours every six hours
and 14 days daily. A 20 GB logical dump can consume hundreds of gigabytes under
that policy; reduce `SNAPSHOT_INTERVAL_MINUTES`, `SNAPSHOT_RETENTION_DAYS` or
disable scheduled libSQL dumps (`SNAPSHOT_LIBSQL_ENABLED=false`) and create
pinned manual snapshots at the cadence the business actually needs.

## 3. Restore procedure

1. Open the database detail page → **Restore points**.
2. Choose a snapshot and **Restore**.
3. The restore creates a **new database**; it never overwrites the live primary.
4. For a libSQL snapshot, the dump is replayed and a fresh primary is
   provisioned. The new database receives a new credential.
5. Validate row counts, critical tables and application login on the new
   database.
6. Point the ERP to the new URL and token only after validation.

The restore request is synchronous while the dump is replayed and the new
primary is provisioned. Allow enough proxy/request timeout for the largest
database, or perform the restore from a maintenance window. The live primary is
never overwritten.

For a production incident:

```bash
# Inspect what will be restored before touching the ERP.
npm --prefix backend run test:external -- \
  "https://<restored-host>" "<new-jwt>" --embedded --deep
```

The `--deep` check writes a temporary table, verifies propagation to an embedded
replica, deletes it and cleans up. Run it against a test or newly restored
database, not the live primary during business hours.

## 4. Token rotation and downtime

**Create new token** performs a guarded rotation:

1. The previous runtime is renamed, stopped and disconnected from the routing
   network.
2. A replacement starts with a new signing key and token.
3. The replacement must accept an authenticated query.
4. Only then is the previous runtime removed and the new credential persisted.

If the replacement fails, the backend restores the previous `auth.pem`, renames
the old runtime back, reconnects it and starts it again. The operation returns an
error explaining whether rollback succeeded.

Rotation is not zero-downtime: it involves a short restart window and the old
token stops being valid after success. Schedule it during a maintenance window
and update the ERP immediately.

## 5. Runtime health

The backend persists internal, backend and public route health. A monitor
refreshes stale results every 10 minutes and on startup, so health survives
backend restarts.

Configuration:

```env
RUNTIME_HEALTH_INTERVAL_MINUTES=10
RUNTIME_HEALTH_PUBLIC_TIMEOUT_MS=5000
RUNTIME_HEALTH_STARTUP_DELAY_SECONDS=20
```

A public health success means the backend resolved the host through DoH and
completed an authenticated query against the public URL. It does not prove that
an ERP's machine, corporate DNS or firewall can reach the same host. For that,
run the external test from the ERP network.

## 6. Performance model

The Studio now:

- asks for schema metadata with `counts=0`;
- caches schema by `PRAGMA schema_version`, so repeated opens avoid re-reading
  every table;
- batches libSQL metadata reads per chunk instead of two round trips per table;
- loads the exact row count only for the table being opened.

The dashboard samples Docker stats with limited concurrency and serves a short
cache (`METRICS_CACHE_TTL_MS`, default 5000 ms).

Important limits:

- Increasing `DB_CONNECTION_POOL_MAX_SIZE` does not increase SQLite write
  throughput. Measure lock contention, transaction duration and disk latency.
- `SQLITE_PERFORMANCE_PROFILE` tunes the backend's local SQLite client. It does
  not change the `sqld` primary's configuration.
- `COUNT(*)` on a huge table is a full scan. The Studio caches it per session and
  refreshes it after writes to that table.

## 7. Turso Cloud → LibSQLite cutover

### Before the window

1. Inventory every ERP database: size, tables, triggers, FTS/virtual tables,
   extensions, write rate and acceptable RPO/RTO.
2. Create a test database in LibSQLite and import a recent copy.
3. Run the deep external test from the ERP's network.
4. Record the exact ERP environment variables and the current Turso values.

### Migration window

1. Stop writes in the ERP (or put it in maintenance mode).
2. Export a final consistent copy from Turso.
3. Import it through the panel or **Server path**.
4. Validate schema objects, row counts and critical queries.
5. Change only the ERP environment:

   ```env
   TURSO_DATABASE_URL=file:/persistent/insbarrera.db
   TURSO_SYNC_URL=libsql://<host>
   TURSO_AUTH_TOKEN=<new-token>
   ```

6. Start the ERP and verify the embedded replica syncs.
7. Exercise login, a read and a write. Confirm the write appears in the primary.
8. Keep the old Turso database read-only until the observation period ends.

### Rollback

After the ERP has accepted writes in LibSQLite, reverting the URL is not enough:
those writes do not exist in Turso. Rollback requires exporting the LibSQLite
database and importing it back, or replaying the delta. Decide this before the
cutover and keep the first hours low-risk.

## 8. Command reference

```bash
# Local migration from legacy LOCAL-FILE to a managed primary.
npm --prefix backend run migrate:local-to-primary -- --mode=runtime --dry-run
npm --prefix backend run migrate:local-to-primary -- --mode=runtime --apply

# Remote + embedded replica + propagation test.
npm --prefix backend run test:external -- \
  "libsql://<host>" "<jwt>" --embedded --deep

# Backend tests (99+ tests) and full quality gate.
npm --prefix backend test
npm test
```

Useful server checks:

```bash
docker logs --tail 200 <backend-container>
docker logs --tail 200 <runtime-container>
docker inspect <runtime-container> --format '{{json .State.Health}}'
```

## 10. First deployment of libSQL snapshots

Before enabling scheduled libSQL dumps on a production ERP:

1. Deploy with `SNAPSHOT_LIBSQL_ENABLED=false` if you want to choose the first
   window manually.
2. Create one manual snapshot from the panel and confirm it reaches **Ready**
   with the **SQL dump · verified** badge.
3. Download it and restore it into a test database; validate row counts.
4. Set the retention aggressively enough for the database size.
5. Enable scheduled dumps and monitor disk, WAL growth and the first run.

## 11. Known boundaries

- A single VPS remains a single point of failure. Snapshots restore data; they
  are not high availability.
- `latest` as the libSQL image tag can change the engine on redeploy. Pin the
  image digest or a specific release for production.
- HTTP `/dump` is a logical export. It can be slower than a physical copy for
  very large databases; measure the restore time with a real copy.
- The public route, certificate and DNS are separate from the data backup. A
  successful snapshot does not imply a working public hostname.
